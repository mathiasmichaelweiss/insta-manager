Приложение уже умеет: авторизацию (Instagram login, `graph.instagram.com`),

большинство задач ниже это вычисления поверх файлов, которые уже лежат на диске.

### Правила

- Всё, что загружается и выгружается — JSON, в `data/`.
- Интерфейс на русском, стиль — токены из `src/app/globals.css`, обе темы.
- Новые выгрузки добавлять как `kind` в существующий `/api/export`.
- Не ломать имеющиеся роуты; после изменений прогонять `npx tsc --noEmit` и `npm run build`.
- Ошибки API показывать текстом с причиной, а не пустым состоянием — см. как
  сделано предупреждение о скрытых комментариях в `redactionWarning`.

### ⚠️ follows и подписки: чего не существует

`follows`, `profile_visits` и `profile_activity` Instagram отдаёт **только для
постов ленты и Stories**. Для Reels API отвечает прямым отказом: *«The Media
Insights API does not support the follows metric for this media product type»*.

Для этого аккаунта (52 Reels из 66 постов) это значит, что сумма `follows` по
постам — **8 за полгода** — описывает 14 постов из 66 и ничего не говорит о
реальности. Честная цифра берётся на уровне аккаунта: **+2 017 подписчиков за
30 дней**. Расхождение в 250 раз.

Что сделано, чтобы это больше не вводило в заблуждение:

- Недоступные метрики **записываются** в `unavailable` каждого файла Reels с
  причиной от Meta. Раньше их там просто не было, и пробел выглядел как ноль.
  Отсутствующее поле означает «метрики не существует», а не «ноль».
- Прирост по аккаунту собирается через `follower_count` (`src/lib/accountInsights.ts`,
  `GET /api/account-insights?refresh=1`) и показан карточкой на вкладке
  «Эффективность».
- В брифе для агента появились `account.newFollowers30d/7d` и раздел `dataNotes`
  с этими оговорками — иначе агент примет отсутствие метрики за ноль.

**Ограничения самого источника.** `follower_count` — новые подписчики за день,
отписки Instagram не вычитает. За один запрос отдаётся максимум 30 дней, поэтому
история копится только с момента первого сбора; собранное сливается в
`data/account-insights.json` по дням.

**Приписать подписки конкретному ролику нельзя в принципе** — ни обходным путём,
ни другой схемой авторизации. Этих данных у Meta для Reels нет.

### Ограничения, о которые не стоит биться

- **Авторы комментариев в основном скрыты.** На разобранном посте имя пришло у 66
  из 449 комментариев. Аналитика «кто мои постоянные комментаторы» невозможна.
- **Истории метрик не существует.** API отдаёт снимок на момент запроса. Динамику
  можно копить только вперёд (T8), задним числом — никак.
- **Конкуренты.** `business_discovery` доступен только в схеме с Facebook-логином
  и отдаёт крохи. Не стоит возни.
- **Stories** живут 24 часа: их статистику надо опрашивать регулярно, иначе она
  теряется. Отдельная задача, в списке ниже нет.

## ✅ T2. Массовая транскрипция — сделано

**Общий движок.** Все три массовые загрузки построены на `streamSync` из
`src/lib/sync.ts` (сервер) и хуке `useSync` из `src/components/useSync.ts`
(клиент). Новую массовую операцию добавлять так же: подготовить список постов,
передать в `streamSync` функцию-обработчик одного поста. У неё есть параметр
`concurrency` — для запросов к Instagram держать 1, для OpenAI можно 3.

Выгрузки `all-insights` и `all-transcripts` добавлены в `/api/export`.

# Аналитика без внешних вызовов

## ✅ T3 + T4. Таблица эффективности с удержанием — сделано

Переключатель «Содержание / Эффективность» на `/posts`, состояние вида хранится в
URL (`/posts?view=performance`), так что на отсортированную таблицу можно дать
ссылку. Колонки: охват, просмотры, досмотр, пропуски, ER, сохранения и репосты на

Производные показатели считает `src/lib/metrics.ts`, отдаёт `GET /api/metrics`.
Определения там одни на всё приложение — новые расчёты добавлять туда же.
Всё нормировано на охват: сырые лайки льстят старым постам, у них было больше
времени.

Досмотр = `ig_reels_avg_watch_time ÷ длительность`. Длительность Instagram не
отдаёт, она берётся из транскрипта — поэтому досмотр есть только у расшифрованных
роликов (51 из 65), и таблица об этом честно предупреждает.

# Аналитика через LLM

Ключ OpenAI уже настроен. Комментарии короткие, проходы стоят центы.

## ✅ T9. Разбор комментариев на темы — сделано

Страница `/topics`, движок в `src/lib/topics.ts`, результат в `data/topics.json`.
Разобрано 4 048 комментариев за ~$0.10, получилось 22 темы и 724 вопроса.

**Как устроено — три прохода, и это не запас прочности.** Пассаж «классифицируем
батчами, каждый батч сам придумывает ярлыки» даёт сорок почти одинаковых тем,
которые нельзя сложить. Поэтому: сначала по выборке из 600 комментариев строится
фиксированная таксономия, потом по ней классифицируется весь архив, потом второй
проход по тому, что осталось в «Прочем».

**Второй проход обязателен.** Без него в «Прочее» уходило 74% архива:
классификатор осторожничает и валит туда всё сомнительное. Отдельная таксономия
для остатка снизила долю до 18%.

**Промпт для таксономии требует покрытия.** Первая версия запрещала темы вроде
«поддержка и согласие» как неинформативные — и вся масса реакций провалилась в
«Прочее». Такие темы нужны: комментариев-реакций больше, чем вопросов.

**Реакции без текста не отправляются в модель** — 169 штук вроде «❤️», токены за
них платить не за что.

**Записи в файл сериализованы.** Четыре параллельных батча пишут один
`topics.json`; без цепочки промисов медленная ранняя запись затирала более полную
позднюю, и в файле оказывалось меньше данных, чем было классифицировано.

Модель настраивается через `OPENAI_ANALYSIS_MODEL`, по умолчанию `gpt-4o-mini`.

## ✅ T14. Черновики и бриф для ИИ-агента — сделано

Страница `/drafts`. Загрузка видео, которого ещё нет в Instagram → транскрипция
через тот же движок, что и для опубликованных роликов (`transcribeLocalFile` в
`src/lib/transcribe.ts`). Видеофайл не сохраняется — только транскрипт: копия
гигабайтов в `data/` не даёт ничего, файл и так лежит у пользователя.

**Бриф** (`src/lib/brief.ts`, `GET /api/export?kind=brief&draft=<id>`) собирает в
один JSON: медианы аккаунта, все посты с метриками и полными транскриптами,
хуки (первые 5 секунд речи), темы комментариев с числом вопросов и сам черновик.
Посты отсортированы по охвату — агент читает победителей первыми. «Прочее» из тем
исключено: это корзина остатков, в брифе она была бы шумом. Размер ~220 КБ на
65 постов, около 50 тысяч токенов — влезает в контекст без ухищрений.

Расширение файла приводится к белому списку форматов OpenAI, имя от пользователя
до файловой системы не доходит.

**Сборка выдаёт 3 предупреждения Turbopack** про динамический доступ к файловой
системе (два из них были и раньше, в `transcribe.ts`). Они про размер бандла при
деплое и локальному запуску не мешают.

## T10. Анализ хуков

**Зачем.** Пожалуй, самое ценное, что можно выжать из этих данных.

**Что сделать.** Из каждого транскрипта взять первые 3–5 секунд (сегменты уже с
таймкодами) — это хук. Свести таблицу «хук → удержание → доля пропусков →

достаточно прочитать глазами, чтобы увидеть закономерность. LLM опционально —
сформулировать, чем отличаются сильные хуки от слабых.

**Зависит от.** T1, T2, T4.

# Сигнал под вопросом

Обе задачи реализуются дёшево, но на текущих данных, скорее всего, дадут шум.
Делать осознанно, понимая ограничение.

## T11. Эффективность хэштегов

**Что сделать.** Парсинг подписей (уже на диске), группировка по тегам, медианный
охват и ER на тег.

**Оценка.** S.

**Почему сигнала может не быть.** Набор тегов повторяется почти дословно от ролика
к ролику. Без разброса корреляцию считать не из чего — получится красивая таблица,
которая ничего не скажет. Имеет смысл, только если начать осознанно варьировать наборы.

## T12. Время публикации

**Что сделать.** Сводка «день недели × час» против медианного охвата.

**Оценка.** S.

**Почему сигнала может не быть.** 65 постов на 168 ячеек сетки — в среднем меньше

День недели отдельно от часа ещё может что-то дать, час — почти наверняка шум.
Решений на этом лучше не строить.
